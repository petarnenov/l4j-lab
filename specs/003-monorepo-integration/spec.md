# Feature Specification: Monorepo Integration

**Feature Branch**: `003-monorepo-integration`

**Created**: 2026-09-12

**Status**: Implemented, 2026-09-12. All 37 tasks in `tasks.md` are complete; quickstart Scenario 7 (CI selection on GitHub) is deferred until a remote exists.

**Input**: User description: "Monorepo integration (option B from the architecture review). The repository root already holds backend/ (Gradle, Micronaut) and frontend/ (npm, Vite, React) but they are not wired together. Goals: (1) the OpenAPI description generated by Micronaut OpenAPI is written to a stable location whose name does not carry the application version, so frontend generate:api and check:api do not break when the version changes and do not depend on a manual build order; (2) a single root verification command (./gradlew check) runs the backend tests, the frontend Vitest suite, and the contract drift check (schema.d.ts vs the generated OpenAPI), failing when the committed frontend types are stale; npm remains the frontend's own build tool, Gradle only invokes it; the live model test stays excluded; (3) one project name and one version across Gradle, OpenAPI, and npm; (4) CI with path-aware jobs for backend, frontend, and the contract check; (5) README documents the root-level commands. Out of scope: Nx/Turborepo/pnpm workspaces, splitting into multiple repositories, changing application behavior. Audience: learners and maintainers of the teaching project who clone one repository."

## Context

The repository already has the shape of a monorepo: the backend, the frontend, the shared
specifications, the container definitions, and one README sit under a single root. What it lacks is
the wiring. The two halves are verified separately, by commands a person has to remember, in an order
a person has to know.

Three concrete gaps motivate this feature, each observed in the current tree:

- The frontend's contract scripts read the published API description from inside the backend's build
  output, by a file name that embeds the application version (`financial-agent-chain-0.1.yml`).
  Changing the version, or running the frontend script before the backend has been built, breaks
  them.
- The root verification command checks only the backend. The frontend's 120 tests and the check that
  its committed API types still match the backend run only when someone runs them by hand. A Java
  record can change, the build can pass, and the frontend types can silently go stale, which is
  exactly the double declaration Principle III forbids.
- The project carries three names (`l4j-lab`, `financial-agent-chain`,
  `financial-agent-chain-frontend`) and two version spellings (`0.1`, `0.1.0`) for one application.

The application's behavior does not change. Nothing a learner sees in the running application is
different after this feature. What changes is how the repository is verified and how a newcomer
learns to verify it.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - One command verifies the whole project (Priority: P1)

A learner or maintainer clones the repository and, from its root, runs one documented verification
command. That command runs every default backend test, every frontend test, and the check that the
frontend's committed API types match the API the backend describes. It succeeds only if all three
succeed. It never reaches a live model provider and needs no credential.

**Why this priority**: This is the change that turns co-located folders into one project. It closes
the gap where a contract change passes verification while the frontend is broken, which is the
largest risk in the current tree. It stands alone as a shippable improvement even without CI or
naming work.

**Independent Test**: On a clean clone with the prerequisites installed, run the root verification
command once and confirm it runs the backend suite, the frontend suite, and the contract check, and
exits successfully. Then introduce each failure below and confirm the same command fails.

**Acceptance Scenarios**:

1. **Given** a clean clone with no prior build output, **When** the maintainer runs the root
   verification command, **Then** the backend tests, the frontend tests, and the contract check all
   run without any other command being run first, and the command succeeds.
2. **Given** a backend API type has gained a field and the frontend's committed types were not
   regenerated, **When** the root verification command runs, **Then** it fails and its output names
   the contract check as the failing step and says how to regenerate the types.
3. **Given** a frontend test fails, **When** the root verification command runs, **Then** the
   command fails and the output identifies the frontend suite as the cause.
4. **Given** no model credential is configured, **When** the root verification command runs,
   **Then** it does not attempt a live model call and does not fail or skip because of the missing
   credential.
5. **Given** the maintainer wants to run the live model test, **When** they look for it, **Then** it
   remains a separate, deliberately invoked command that the root verification command never runs.

---

### User Story 2 - The contract link survives a version change (Priority: P2)

A maintainer bumps the application version. The frontend's scripts that generate and check the API
types keep working without edits, because they read the API description from a location that does
not depend on the version and does not require the maintainer to remember a build order.

**Why this priority**: This removes the most fragile single point in the current wiring. It is
needed for User Story 1 to stay correct over time, but a project that never changes its version
would not notice its absence immediately.

**Independent Test**: Change the application version in its single declared place, run the type
generation and the contract check from the frontend, and confirm both work unchanged. Delete all
backend build output first and confirm the frontend scripts either produce the description they need
or fail with a message naming the command to run.

**Acceptance Scenarios**:

1. **Given** the application version is changed, **When** the maintainer runs the frontend's type
   generation or contract check, **Then** both succeed with no edit to the frontend scripts.
2. **Given** there is no backend build output at all, **When** the maintainer runs the frontend's
   contract check on its own, **Then** it fails with a message that names the missing API description
   and the command that produces it, rather than an unexplained "file not found".
3. **Given** the root verification command runs on a clean clone, **When** it reaches the contract
   check, **Then** the API description has already been produced by an earlier step in the same run.

---

### User Story 3 - One name and one version for one application (Priority: P3)

A learner reading the build file, the API description, and the frontend manifest sees the same
project name and the same version in each. The version is declared once and the others follow from
it or match it exactly.

**Why this priority**: It removes a source of confusion for readers of a teaching project, but
nothing is broken by the current mismatch.

**Independent Test**: Read the project name and version from the backend build, the generated API
description, and the frontend manifest, and confirm they agree.

**Acceptance Scenarios**:

1. **Given** the repository after this feature, **When** a reader compares the project name in the
   build, the API description title, and the frontend package name, **Then** they share one base name.
2. **Given** the version is changed in its single declared place, **When** the project is built,
   **Then** the API description reports the new version, and a verification step fails if the
   frontend manifest's version does not match.

---

### User Story 4 - Continuous integration runs only what a change touches (Priority: P3)

A maintainer pushes a change. Automated checks run the backend suite when backend files change, the
frontend suite when frontend files change, and the contract check when either side changes. A change
confined to documentation or specifications runs neither test suite.

**Why this priority**: It depends on User Story 1 being in place and on the repository being hosted
somewhere with automation. It saves time and makes failures legible, but local verification already
guarantees correctness.

**Independent Test**: Push three changes in turn, one touching only the frontend, one only the
backend, one only a specification, and confirm which checks run for each.

**Acceptance Scenarios**:

1. **Given** a change touches only frontend files, **When** automation runs, **Then** the frontend
   suite and the contract check run and the backend suite does not.
2. **Given** a change touches only backend files, **When** automation runs, **Then** the backend
   suite and the contract check run and the frontend suite does not.
3. **Given** a change touches only the build configuration shared by both halves, **When**
   automation runs, **Then** every check runs.
4. **Given** a change touches only documentation or specifications, **When** automation runs,
   **Then** neither test suite runs.
5. **Given** any automated run, **When** it executes, **Then** it never runs the live model test and
   never needs a model credential.

---

### User Story 5 - The README teaches the root-level workflow (Priority: P3)

A newcomer reads the README and learns, in one place, the single command that verifies everything,
how to regenerate the frontend's API types after a backend change, and that the live model test is a
separate deliberate step.

**Why this priority**: Without it the new command exists but a learner does not know to use it.
It is small and follows the other stories.

**Independent Test**: A reader who has not seen this feature follows only the README and verifies
the project, then regenerates the API types after a deliberate backend type change, without reading
build files.

**Acceptance Scenarios**:

1. **Given** the README, **When** a newcomer looks for how to test the project, **Then** the root
   verification command is listed first, with the per-half commands after it.
2. **Given** a contract check failure, **When** the newcomer follows the README's instruction for
   it, **Then** regenerating and re-running the check makes it pass.

---

### Edge Cases

- **Frontend dependencies not installed**: The root verification command installs them from the
  committed lock file, or fails naming the missing prerequisite. It never silently skips the
  frontend suite.
- **Node.js not available**: The command fails with a message naming the missing runtime and the
  version required, rather than an opaque process error.
- **Docker not running**: Backend database tests keep their existing behavior of skipping with a
  named message. The root verification command does not turn that skip into a failure, and the
  frontend suite and contract check still run.
- **Regenerated types differ only in formatting**: The contract check compares the generated output
  byte for byte against the committed file, so formatting drift counts as drift. The README tells the
  maintainer to regenerate rather than hand-edit.
- **A maintainer edits the committed types by hand**: The contract check fails, exactly as for a
  stale file.
- **Two different versions declared**: The frontend manifest's version is made to disagree with the
  application version; verification fails naming both values.
- **Running a single half**: The existing per-half commands (backend tests only, frontend tests
  only) keep working on their own, so the root command is additive, not a replacement.
- **Port or proxy target differences**: The development proxy target is unchanged by this feature;
  aligning it is out of scope.

## Requirements *(mandatory)*

### Functional Requirements

**Contract location**

- **FR-001**: The API description generated from the backend types MUST be available at one fixed
  location in the repository whose path does not contain the application version.
- **FR-002**: The frontend's type generation and contract check MUST read the API description from
  that fixed location.
- **FR-003**: When the API description is absent, the frontend's contract check MUST fail with a
  message naming the file it expected and the command that produces it.
- **FR-004**: The API description MUST still be generated from the backend types and never
  maintained by hand (constitution, Principle III and the Application framework constraints).

**Root verification**

- **FR-005**: A single command run from the repository root MUST execute the default backend test
  suite, the frontend test suite, and the contract check.
- **FR-006**: That command MUST produce the API description before running the contract check,
  without the user running any other command first.
- **FR-007**: That command MUST fail if any of the three fails, and its output MUST identify which
  one failed.
- **FR-008**: That command MUST NOT run the live model test and MUST NOT require a model credential
  or network access to a model provider.
- **FR-009**: The frontend MUST continue to be built and tested by its own package tooling. The root
  command invokes that tooling; it does not replace it or reimplement its steps.
- **FR-010**: The existing per-half commands for backend tests, frontend tests, and the live model
  test MUST keep working unchanged.
- **FR-011**: The root command MUST install frontend dependencies from the committed lock file when
  they are missing, and MUST fail with a named prerequisite when the frontend runtime is unavailable.

**Naming and version**

- **FR-012**: The project MUST use one base name across the build configuration, the API description
  title, and the frontend package name.
- **FR-013**: The application version MUST be declared in one place. The API description MUST report
  that version, and verification MUST fail if the frontend manifest's version differs from it.

**Continuous integration**

- **FR-014**: Automated checks MUST run on every proposed change and select which checks run by the
  paths the change touches: backend paths run the backend suite and the contract check; frontend
  paths run the frontend suite and the contract check; shared build configuration runs everything;
  documentation and specification paths run no test suite.
- **FR-015**: Automated checks MUST NOT run the live model test and MUST NOT be given a model
  credential.
- **FR-016**: Automated checks MUST use the same root-level and per-half commands a maintainer uses
  locally, so a local pass predicts an automated pass.

**Documentation and governance**

- **FR-017**: The README MUST document the root verification command first, then the per-half
  commands, the type regeneration step, and the live model test as a separate step.
- **FR-018**: The feature plan MUST record whether the root build invoking the frontend tooling
  requires a constitution amendment, and MUST either include that amendment or justify why none is
  needed against the Language and build constraints.
- **FR-019**: No application behavior, API shape, database migration, or user-facing screen may change
  as part of this feature.

### Key Entities

- **API description**: The machine-readable description of the backend's HTTP API, generated from
  the backend types. Has a title (the project name), a version (the application version), and one
  fixed repository location.
- **Committed frontend API types**: The generated type file the frontend compiles against. Must be
  byte-identical to what regeneration from the current API description produces.
- **Root verification command**: The one documented entry point that runs every default check for
  both halves and the contract between them.
- **Project identity**: The single base name and single version shared by the build, the API
  description, and the frontend manifest.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: From a clean clone with prerequisites installed, one command run once verifies the
  whole project, with zero additional commands required beforehand.
- **SC-002**: In 100 percent of trials where a backend API type is changed without regenerating the
  frontend types, root verification fails and names the contract check.
- **SC-003**: Changing the application version requires editing exactly one declaration, and the
  frontend type generation and contract check succeed afterwards with zero script edits.
- **SC-004**: Reading the project name and version from the build, the API description, and the
  frontend manifest yields one name and one version in all three.
- **SC-005**: A change touching only documentation or specifications completes automated checks
  without running either test suite; a change touching one half runs that half's suite and the
  contract check only.
- **SC-006**: A newcomer following only the README verifies the project and resolves a deliberately
  induced contract failure without opening a build file.
- **SC-007**: The test counts reported by the per-half commands before and after this feature are
  identical, confirming no test was lost or silently skipped by the new wiring.

## Assumptions

- The repository has just been placed under version control, and the existing directory layout
  (`backend/`, `frontend/`, `specs/`, root build files) stays as it is. No files move between halves.
- The shared base name defaults to `financial-agent-chain`, because the README, the API description,
  and the frontend package already use it; only the root build name changes. The plan may revisit
  this.
- The application version remains `0.1.0` in semantic form, declared once in the backend build.
- The CI host is GitHub Actions, chosen by the maintainer on 2026-09-12 during planning. No remote
  exists yet. The requirements above are written to hold on any host that supports path-based job
  selection.
- Node.js is a documented prerequisite, like the JDK toolchain and Docker. Whether the build
  provisions Node itself or requires it on the machine is a plan decision, weighed against the
  constitution's aim that commands do not depend on what happens to be installed.
- Committing the generated API description itself, as opposed to only the frontend types derived
  from it, is a plan decision. Either way the description stays generated, never hand-written.
- Out of scope: monorepo orchestration tools (Nx, Turborepo, pnpm workspaces), splitting into
  multiple repositories, aligning the development proxy port, and any change to application behavior.
